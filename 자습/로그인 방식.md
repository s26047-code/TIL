# 로그인 방식
#### 사용자가 로그인하면 서버는 데이터베이스로 정보를 확인한 뒤, 쿠키·세션·JWT 등을 이용해 사용자의 로그인 상태를 유지한다

로그인 방식은 웹사이트가 **사용자를 식별**하고, 개인 정보 보호와 서비스 이용 권한을 안전하게 관리하기 위해 필요
 
<br>
<br>
<br>

## 쿠키
#### 쿠키(Cookie)는 사용자의 브라우저에 데이터를 저장하여 사용자를 식별하거나 정보를 유지하는 방식이다
사용자가 웹사이트에 접속하면 서버는 필요한 정보를 작은 데이터 형태로 **브라우저에 저장**하는데, 이것이 바로 쿠키다.

이후 사용자가 다시 같은 웹사이트에 요청을 보내면 브라우저는 저장된 쿠키를 서버에 자동전송하고, 서버는 쿠키의 정보를 확인하여 사용자를 식별하거나 이전 상태를 유지한다.


> #### 장점
> - 브라우저에 직접 저장되므로 서버의 부담이 적음



> #### 단점
> - 컴퓨터에 저장되므로 중요한 정보는 보안 문제가 생길 수도 있음


실제 서비스에서는 비밀번호 같은 중요정보는 저장하지 않고, ID 같은 간접적인 정보만 저장하는 경우가 많다.

## 세션
#### 세션(Session)은 사용자가 로그인했을 때 서버가 사용자의 정보를 일정 시간 저장해두는 방식이다.

세션 방식으로 사용자가 로그인하면 서버는 아이디와 비밀번호를 **데이터베이스에 사용자 정보를 저장**한다.
이때 서버가 사용자를 구별하기 위한 고유한 세션 ID를 생성한다.

그리고 이 세션 ID를 쿠키로 담아 사용자 브라우저로 보낸 후,
사용자가 다른 페이지를 요청하면 브라우저는 쿠키에 저장된 세션 ID를 서버에 함께 전송하게 된다.

서버는 전달받은 세션 ID를 확인하여 저장된 사용자 정보와 비교하고, 같은 사용자임을 확인하면 로그인 상태를 유지한다

> 요약 <br>
> - 실제 로그인 정보는 서버에 저장되고, 브라우저에는 사용자 구별용 번호인 세션 ID만 저장됨

세션 방식은 중요한 정보는 서버에 저장되기에 비교적 보안성이 높지만, 사용자가 많아질수록 서버가 저장해야 하는 데이터도 증가한다.

## JWT (JSON Web Token)

#### JWT는 인증 정보를 JSON 형태로 담아 서버-클라이언트 간에 안전하게 주고받기 위한 토큰이다.

일반적인 세션 방식은 서버에 로그인 상태를 저장해두는 방식인데, JWT는 서버에 상태를 저장하지 않고 **토큰 자체**에 정보를 담는 방식이다.

ㄴ> 이 방식을 **Stateless** 방식이라고 하며, 서버 부담을 줄이고 확장에 유리하다.




JWT는 `.`으로 구분된 세가지로 구성된다.

| 구분 | 역할 |
|---|---|
| **Header** | 토큰 타입과 암호화 알고리즘 정보 |
| **Payload** | 실제 담을 데이터 (사용자 ID, 권한 등) |
| **Signature** | 위·변조 방지를 위한 서명값 |

ㄴ> 단, Payload는 Base64로 인코딩된 것일 뿐 암호화가 아니기 때문에 비밀번호 같은 민감한 정보는 담으면 안 된다. <br>
- base64란 이진 데이터 텍스트로 변환하는 인코딩 방식
<br>
<br>

### JWT 동작 흐름

```
1. 클라이언트 → 서버 : 로그인 요청 (아이디 + 비밀번호)
2. 서버           : 사용자 확인 후 JWT 생성
3. 서버 → 클라이언트 : JWT 토큰 발급
4. 클라이언트 → 서버 : 이후 요청 시 토큰을 Header에 보냄
5. 서버           : 토큰 서명 검증 후 요청 처리
```

## 요약

| 방식  | 저장 위치  | 특징            | 장점        | 단점       |
| --- | ------ | ------------- | --------- | -------- |
| 쿠키  | 브라우저   | 사용자 정보 저장     | 빠르고 간단함   | 보안 약함    |
| 세션  | 서버     | 서버가 로그인 정보 관리 | 보안 높음     | 서버 부담 증가 |
| JWT | 브라우저/앱 | 토큰으로 인증       | 서버 부담 적음  | 탈취 위험    |
