이 과정의 대표적인 두가지 아키텍처가 있으며, 이 아키텍처<span style="color: gray;">(설계 구조)</span>에 따라서 배포 방식을 결정하게 된다.

# 모놀리식 아키텍처
Monolithic Architecture의 약자로 **전통적인 개발 방식**이다. 하나의 프로젝트에 모든 기능을 개발하게 된다.

하지만 프로젝트의 <mark>규모가 커질수록 배포 및 복잡성</mark>의 문제가 생긴다는 단점이 있다.

<br>

초기 개발에 유리하고 호출 역시 간단해 복잡한 통신이 필요하지 않으나, 유지관리 및 확장이 어렵고 일부 기능을 수정하거나 **간단한 업데이트에도 전체 재배포**가 필요해져버린다.

<br>

그러므로 적은 개발 인원과 **소규모 프로젝트** 및 단기 프로젝트에 적절한 아키텍처 방식이라고 정리할 수 있다.

<br>
<br>
<br>
<br>

# MSA

MicroService Architecture의 약자로,**독립적으로 배포 가능한 각각의 기능을 수행하는 아키텍처 스타일**을 의미한다. 

작은 서비스들이 독립적으로 개발되고 배포되는 구조를 가지고 있다.

<br>

MSA 방식의 경우 전체 시스템이 분산되어 있어 <mark>확장성과 유지관리가 용이</mark>해진다는 장점이 있다. 하지만 독립적인만큼 서비스 간 통신을 필수로 하며, 연결 구축 및 관리의 복잡성이 늘어난다.

<br>

그러므로 많은 개발 인력과 확장이 필요한 **대규모 및 복잡한 프로젝트**에 적합한 아키텍처 방식이라고 정리할 수 있다.

<br>
<br>

> ## <span style="color: gray;">MSA의 구성요소</span>
>
> <span style="color: gray;">MSA는 여러 서비스가 독립적으로 구성되기 때문에 서비스 간 통신과 설정 정보 관리가 중요하므로 **API Gateway**, **Vault**, 와 같은 구성 요소를 사용한다.</span>

> ### <span style="color: gray;">API Gateway</span>
>
> <span style="color: gray;">여러 서비스로 들어오는 요청을 **하나의 진입점에서 받아 각 서비스로 전달**해주는 출입구 역할을 한다.
>
>
> <span style="color: gray;"> 1. 클라이언트에서 Gateway에 요청한다.<br>
> 2. 요청 URL이나 조건에 따라 적절한 서비스로 **라우팅**한다. <br>
> 3. 인증/인가를 Gateway가 처리 할 수 있다!
</span>

> ### <span style="color: gray;">Vault</span>
>
> <span style="color: gray;">MSA의 **환경변수** 같은 느낌으로, 민감한 정보들을 중앙에서 관리하는 secret 관리 시스템이다.</span>

> ### <span style="color: gray;">Eureka</span>
>
> <span style="color: gray;">MSA는 **서버마다 IP와 Port가 다르므로, 서비스를 중앙에서 관리하기 위해** 각 정보들을 한 곳에 등록해두고, Gatewqy가 조회하여 사용한다.</span>





<br>
<br>
<br>
<br>

### 그런데 MSA를 알아보니 하나 의문이 생기게 된다.

MA에서는 하나의 애플리케이션에서 여러 기능이 동일한 DB를 사용하기 때문에 하나의 <mark>트랜잭션</mark>으로 여러 데이터의 생성·수정을 묶어 처리할 수 있지만

MSA에서는 서비스별로 데이터베이스를 **독립적으로 관리**한다. 그렇다면 여러 서비스에 걸쳐 데이터를 동시에 생성하거나 수정해야 하는 경우애는 기존처럼 <mark>트랜잭션</mark>으로 묶어서 처리하는 것이 어려워지는 문제가 발생하고 말 것이다!

<br>

> ### <span style="color: gray;">트랜잭션이란?
> 여러 개의 DB 작업을 하나의 작업 단위로 묶는 것이다.
>
> 약칭 ACID인 원자성, 일관성, 독립성, 지속성의 특징을 띄며, 
>
> 보통 하나의 작업으로 묶여 모두 성공해야 하는 일들에 사용된다.
>
> 트랜잭션으로 묶인 작업은 **정상적으로 수행되어야 COMMIT된다. 만약 중간에 문제가 발생하면 ROLLBACK**하여 작업 이전 상태로 되돌아간다. <br> <br>
>   이때 이 COMMIT/ROLLBACK 과정을 <mark>AOP</mark>를 사용하여 처리한다. </span>

<br>

> ### <span style="color: gray;"> AOP란?
> Aspect Oriented Programming의 약자로 스프링에서 공통적으로 사용되는 기능들을 효율적으로 관리하기 위한 기능이다. 이때 AOP의 뜻을 직역하면 관점 지향 프로그래밍이 된다.
>
> 스프링은 이 AOP를 이용하여 위에 설명된 `@Transactional`를 구현 할 수 있게 된다!

<br>
<br>
<br>
<br>

### 그렇다면 MSA에서는 어떻게 트랜잭션을 어떻게 처리해야할까?
대표적으로 두가지 패턴을 사용하여 트랜잭션을 관리한다고 한다.

<br>
<br>

## 2PC 패턴

2-Phase-Commit의 약자이며 <mark>XA<span style="color: gray;"> (eXtended Architecture)</span> 프로토콜</mark>등을 사용하여 구현한다고 한다.

> <span style="color: gray;">**XA 프로토콜**이란, 분산 트랜잭션을 일관되게 처리하기 위해 트랜잭션 매니저와 리소스 매니저 간의 상호작용을 정의한 표준 프로토콜이다.</span>
>
> <span style="color: gray;">트랜잭션의 일관성을 보장하기 위해 트랜잭션 매니저가 리소스 매니저들에게 커밋 준비 여부를 확인하는 **1단계**(Prepare)를 진행한다. 모든 리소스가 준비되었다면 **2단계**(Commit)에서 실제 커밋을 요청하며, **하나라도 준비되지 않았다면 전체 트랜잭션을 롤백**하는 것이다.</span>

<br>

2PC패턴은 **여러 트랜잭션도 하나의 트랜잭션처럼 다룰 수 있게 해줄 수 있고, 모니터링이 가능하다는 장점**이 있지만 모든 기능이 준비되어야 하는 만큼 **대기 시간이 길어 확장이 어려워**진다는 단점 역시 존재한다.

또한 DB와 트랜잭션을 독립적으로 관리하는 구조인 MSA 철학과도 근본적으로 맞지 않는다.

<br>
<br>

## SAGA 패턴
말 그대로 Saga Pattern이며, 각 서비스가 자체적으로 수행하는 로컬 트랜잭션의 흐름을 메시지 또는 이벤트로 이어가는 방식이다. 

커밋을 받지 못한다면 작업 없이 롤백하는 2PC 패턴과 다르게, 첫번째 단계를 성공했는데, 다음 단계에서 실패 시 **이전의 작업을 되돌리는 보상 방식**으로 진행된다.

<br>

SAGA 패턴은 2PC 패턴의 단점을 보완하기 위해 사용되며, 사용하는 방식으론 대표적인 두가지 방식이 있다.

<br>
<br>

### Choreography 방식

중앙 제어 없이 **서비스끼리 이벤트로 통신**하는 방법이다. 서비스들은 동작을 수행하며 이벤트를 스스로 발행하고, 그 트랜잭션을 서비스가 수행한다.

-  트랜잭션이 실패하면 **보상 이벤트**를 발행하여 이전 작업을 취소한다.

-  서비스 간 이벤트 전달 효율을 위해 **Kafka와 같은 메시지 브로커**를 사용(라이브러리 사용 가능)한다고 한다.

- **각 서비스가 이벤트를 받고 자신의 작업을 수행한 뒤 다음 이벤트를 발행**하는 순차적 구조를 가지고 있다고 한다.

<br>
<br>

### Orchestration 방식
**중앙 제어가 전체 프로젝트 흐름을 지시하고 통제**하는 패턴이다. 이 역시 특정 단계에서 실패하면 중앙 제어(오케스트레이터)가 보상 트랙잭션 명령을 내린다.

- 직관적인 흐름을 한눈에 모니터링 가능하다.

- 여러 단계가 엄격히 실행되므로 순서 제어가 유익하다.

- 단, 복잡성이 즐가하고 **오케스트레이터가 다운되면 전체 프로세스가 마비**될 수도 있다.

<br>
<br>

### 다시한번 요약 정리하자면,
SAGA 패턴은 위의 두가지의 방식으로 사용되며, 중간에 작업이 실패하면 이미 완료된 이전 단계들을 취소하는 보상 트랜잭션을 실행하여 최종적인 <mark>데이터 일관성</mark>을 맞춘다.

<br>
<br>
<br>
<br>


## 결론
<mark>SAGA</mark>는 즉시 커밋 후 롤백하기에 독립적이고, 확장성을 가졌기에 MSA에서 주로 사용된다.

**그러므로 SAGA 패턴 중에서도 중앙 제어 없이 사용 가능한 독립적 방식인 `Choreography`를 사용할 거라고 생각할 수 있으나, `Orchestration`를 사용하는 것이 보편적이다.**

<br>

이는 왜냐하면 `Choreography`는 서비스끼리 이벤트만 주고 받기에 단계가 복잡해질수록 언급했던 단점이 발생하기 때문이다.

그러므로 중앙 제어자가 프로세스를 한번에 관리해주고, 모니터링과 트랜잭션이 명확한 `Orchestration`방식이 SAGA 패턴으로써 사용된다.

# MSA 실사용 방법


### 1. Eureka Server 생성

별도의 유레카용 Spring Boot 프로젝트를 생성하고 의존성을 추가한다.

```gradle
implementation 'org.springframework.cloud:spring-cloud-starter-netflix-eureka-server'
```

<br>

### 2. 각 제작한 서비스에 유레카 의존성 추가
```gradle
implementation 'org.springframework.cloud:spring-cloud-starter-netflix-eureka-client'
```
그 후 appilcation에도 유레카 서버 주소를 기입한다. (이 과정을 마치면 해당 서비스가 유레카에 등록되게 된다)

<br>

### 3. Gateway도 Eureka Client로 연결
Gateway에도 유레카 의존성을 추가하고 유레카 서버 주소를 설정한다.

그 후, Gateway에서 서비스 이름을 이용해 라우팅하면 lb://USER-SERVICE를 통해 유레카에 등록된다. 이제 서비스의 위치를 찾아 요청을 전달하면 연동에 성공할 수 있다!

<br>

# AOP 사용과정
AOP는 어떤 로직을 기준으로 핵심적인 관점, 부가적인 관점으로 나누어서 보고 그 관점을 기준으로 기능을 하나의 단위로 묶는 것을 뜻한다.

예를 들어 어떠한 기능을 만들 때 해당 기능의 로그를 남기고 싶다고 가정하자.

만약 AOP를 사용하지 않고 로그를 남기려면, 모든 메서드에 

```gradle
public void class() {
    System.out.println("로그");

}
```
같은 코드를 일일히 작성해주어야 한다.

<br>

그렇지만 나는 그걸 매번 쓰고 싶지가 않다!
그래서 사용하는 것이 바로 AOP 프로그래밍 방식이라고 정리할 수 있겠다.

<br>
<br>

### AOP를 사용한다면?
AOP를 사용하지 않고 어떠한 객체를 호출한다면 당연히 바로 그 객체가 실행되겠지만,

AOP를 사용한다면 <mark>프록시</mark>가 대신 정보를 담은 객체를 호출할 수 있게 해준다.

> ### <span style="color: gray;">프록시란?
> 특정 실제 객체를 대신해서 호출을 받고, AOP 같은 부가 작업을 한 뒤 그 실제 객체로 호출을 전달하는 **대리 객체**이다.
>
> 여러 기능들에 공통 기능을 한번에 호출하고 싶은데, 각 서비스는 모두 다르고 나는 코드를 요약해서 쓰고 싶다.
>
> 그러니 그 객체들을 **대신하여 호출해주는 대리인**이라고 이해하면 될 것이다!

<br>
<br>

### 그렇다면
예시로
로그를 만들어주는 코드를 봐보자.
```gradle
@Around("execution(* com.example.service..*(..))")
public Object logging(ProceedingJoinPoint joinPoint) throws Throwable {

    System.out.println("로그 시작");

    Object result = joinPoint.proceed();

    System.out.println("로그 종료");

    return result;
}
```

<br>

이때 이 코드에서 
```gradle
@Around("execution(* com.example.service..*(..))")
```
이 부분이 바로 어떤 메서드에 AOP를 적용할지 정하는 조건이다.


> com.example.service 패키지 아래에 있는 메서드들에 적용하라는 뜻

> 이를 사용하기 위한 Advice 어노테이션으론 `Before`, `After`, `Around`가 있다.
> Before은 대상 메서드가 실행되기 전에 실행하라는 것이고, After는 반대, Around는 실행 전 후를 감싸 직접 제어한다고 알아두자.

<br>

> **그 외 어노테이션** <br>
> `@Aspect`          → AOP 클래스임을 명시 <br>
`@Pointcut`        → AOP 적용 위치 지정
<br>
`@AfterReturning`  → 메서드가 정상 반환되면 실행
<br>
`@AfterThrowing`   → 예외가 발생하면 실행

<br>
<br>
<br>
<br>


또한 위 코드에서 
```gradle
Object result = joinPoint.proceed();
```
이 부분은 AOP가 가로챈 원래 실행하려던 메서드를 실제로 실행하고, 그 반환값을 result에 저장하는 것을 의미한다.

이 과정에서 프록시는 메서드 호출을 먼저 받아 AOP와 같은 부가 기능을 실행한 뒤, joinPoint.proceed()를 통해 실제 객체의 메서드가 실행되게끔 전달할 수 있다!
