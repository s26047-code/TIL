# HTTP
HTTP란, 웹에서 클라이언트와 서버가 데이터를 주고 받을 때 사용하는 통신 규약이다.
> ex) 웹사이트 접속 -> 서버 **요청** -> **응답**

<br>
<br>

### HTTP Method
- 클라이언트가 서버에 요청할 때 수행하는 동작
 
 > Get(데이터 조회) <br>
 > Post(데이터 생성)<br>
 > Put(데이터 전체 수정) <br>
 > Delete(데이터 삭제) <br>
 > patch(데이터 수정)

  
  <br>
  <br>


  ### HTTP Status Code
  - 서버가 요청 처리결과를 숫자로 바꾸어 나타낸 것 <br>
  <small>ex) 오류가 나면 404 화면이 출력됨</small>

  <br>
  <br>


  ### HTTP의 무상태성
  - 서버가 이전의 요청을 저장하지 않는 상태

    - 각 요청은 독립적으로 처리된다.

> 매 요청마다 필요한 정보가 전달되지 않으면 오류!

# RESTful API

#### http 프로토콜의 장점을 활용하여 자원을 이름으로 구분하고, http 메서드(get, post, put, delete, patch)를 통해 해당 자원의 상태를 교환하는 설계 원칙을 준수한 애플리케이션 인터페이스이다.

(위의 http정리 부분을 참고한다)

### 원칙
> 클라이언트-서버(Client-Server) 구조로, 클라이언트와 서버를 명확히 분리하여 독립적인 개발 및 확장이 가능하게 함


> 각 요청은 독립적으로 처리되어야 하며, 서버는 요청 간의 상태를 저장하지 않아야 함 필요한 모든 상태 정보는 요청에 포함해야 한다.

>계층화 시스템(Layered System) >> 시스템은 계층화되어야 하며, 각 계층은 다른 계층의 동작을 간섭하지 않는다.

>통일된 인터페이스(Uniform Interface) >> HTTP 표준을 따르는 통일된 인터페이스를 사용하여 자원을 조작

<br>
<br>
<br>
<br>


>### 장점?
> http 표준을 따르므로 언어와 플랫폼에 중립적이다.

- 확장성: HTTP 표준을 기반으로 하여 확장이 용이
- 독립성: 클라이언트와 서버의 분리로 독립적인 개발 및 유지보수 가능
- 유연성: 다양한 데이터 형식 지원
- 표준화: 일관된 URI와 HTTP 메서드로 통일된 인터페이스 제공

>### 단점?
> 상태 관리가 필요 없는 경우에 적합함. 즉, 세션관리 어렵고 규칙 준비 어려움
